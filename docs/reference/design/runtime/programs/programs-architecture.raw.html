Programs code structure

Everything the agent can call is a Program. Built-in tools live in programs/tools/ and are always available; built-in applications live in programs/applications/ and can be switched on and off; the user's own Programs live in ~/.openprogram/programs/. Each loaded package registers through its own ProgramContext, so unloading it removes everything it added. Model calls go through two primitives, llm() and agent(), plus the Agent class for named roles.

Status: current designScope: source, registration, Programs UI, packaging

1. Directory layout

openprogram/
├── runtime/agent/
│   ├── llm.py                  # llm(): one model call
│   ├── agent_function.py       # agent(): model tool-call loop
│   └── agent_class.py          # Agent: named roles with methods
└── programs/
    ├── __init__.py             # resolution API: TOOLSETS, DEFAULT_TOOLS, agent_tools, apply_tool_policy
    ├── tools/                  # built-in tools, always given to the Agent
    │   ├── files/  code/  web/  interaction/  knowledge/  jobs/
    │   ├── agents/  computer_use/  runtime/  system/
    │   └── planning/           # todo/  plan_mode/  open_work/  goal/
    ├── applications/           # built-in applications, each enabled or disabled as a unit
    │   ├── browser/            # tabs, Pages and web_use
    │   ├── workflow_recording/ # the demonstration recorder
    │   └── office_editor/      # the ONLYOFFICE document editor
    ├── _authoring/             # what Program code imports: errors, json_parsing, reports/, helpers ...
    └── _host/                  # how the host loads and runs Programs; Program code never imports it
        ├── runtime.py          # @function and the shared tool registry
        ├── context.py          # ProgramContext, one per owner
        ├── registry.py         # loader for built-in, user and harness Programs
        └── packages.py  sources.py  execution.py  services.py  ui/ ...

~/.openprogram/programs//   # the user's Programs: Python packages, applications, harness clones
Each capability has one authoritative implementation and one public import path. There are no functions/, workflows/ or packages/ directories under programs/, and no compatibility aliases for old paths.

2. Three places a Program comes from

programs/tools/

Built-in tools

What the agent cannot work without: files, shell, search, planning, asking the user, memory, jobs, web and computer use. They ship with the core, are always given to the agent and cannot be disabled one by one. Most register with @function on import; a tool package with PROGRAM_ENTRIES registers through its own ProgramContext (owner tool:<name>).

programs/applications/

Built-in applications

browser, workflow_recording and office_editor. Each loads through a ProgramContext owned by application:<name>, provides the named service the core reaches it through, and loads only while enabled (openprogram programs enable|disable <name> or the Applications page).

~/.openprogram/programs/

User Programs

Python packages that list PROGRAM_ENTRIES (Workflows such as a weekly report or a research loop), application directories with application.json, and harness clones recorded by openprogram programs install. They load through the same contexts as built-ins; see Workflows for the package contract.

Portable package sources

Project-local Programs record locations as relative paths scoped by programs. An external installation binding connects the installed runtime to the source checkout. Relative paths do not use the chat working directory. Only exact authorized package names participate in Python resolution; the entire external directory is not added to import scope. Rejection conditions and publishing rules follow the Workflow package contract.

A Workflow is ordinary Python that calls these primitives and other Programs. Any capability that makes model calls, calls other Workflows, or keeps multi-stage state and completion checks is a Workflow; a single model call wrapped in a role is one too.

4. Goal runs as ordinary chat turns

One mechanism
A Goal is session state in programs/tools/planning/goal/. After each successful chat turn, chat.py decides whether to start another ordinary chat turn for the active Goal. There is no separate Goal loop, judge Workflow or nested working agent.
Programs form
goal(prompt) takes only the objective. It saves a chat Goal in the current conversation and the route starts the first turn through the same controls as /goal.
Chat command and agent tools
/goal <objective> and the agent's create_goal tool create the same chat Goal. The goal Program is never offered to agents as a tool.
Completion
update_goal(status="complete") or a finished todo plan only submits a candidate. verification.py runs one independent read-only verification turn before the Goal becomes achieved.
Limits and restarts
Goals have no round limit. Two automatic turns in a row without a tool call stop the Goal as stalled. Optional token, active-time and cost limits are the only budgets. A Goal whose lease belonged to a previous worker comes back paused with a resume action (restart.py).

7. Registration and Programs UI

Shared registration
_host/registry.py loads built-in tools, enabled built-in applications, the user's Programs and recorded harnesses. Every package registers through its own ProgramContext, kept by owner (tool:<name>, application:<name>, the user package's name, external:<package>); unloading or reloading disposes it.
Programs tree
The tree mirrors source directories only. A registered entry is runnable and shows Use. Expanding a same-name package lists its modules from the actual directory (such as goal/command.py); these can be opened to read but are not registered as extra Programs. __init__.py and _ directories never become nodes.
Stable contract
Moving source does not change public names, parameter schemas, permissions, DAG semantics or session state formats. Old paths fail directly; there are no aliases or dual scanning.

8. Excluded designs

No workflow decorator

There is no @workflow; directories and metadata express classification.

No string-based dispatch

Workflows use ordinary Python imports and calls; there is no call_workflow(name).

No parallel structures

No versioned old/new directories and no runtime choice between them.

9. Dynamic tool argument mappings

Canonical tool schemas distinguish mappings whose keys are provided at invocation time from objects with declared fields. The public program.args mapping accepts a registered program's legal keyword arguments, including task. Anonymous object mappings and Python dict/Mapping annotations keep open keys and any declared value schema. Objects with properties, including an empty declared property set, keep fixed-field closure. Explicit additionalProperties: false is never opened; nullable mappings keep their null behavior.

Canonical objectLocal validationProvider tool mode
Anonymous or typed mappingAccept legal dynamic keys; enforce object and declared value typesKeep the mapping schema with non-strict tool mode
Declared fixed fields or explicit closed objectKeep required fields, types and closed-field rejectionStrict mode where supported
Mixed request containing both tool kindsValidate each call against its canonical schemaSelect mode per tool; strict validation is never disabled request-wide

The shared provider schema adapter never turns an open mapping into an empty closed object: models/providers/schema/strict.py refuses to make a schema with dynamic keys strict. OpenAI function calling requires closed objects for strict mode, so dynamic-mapping tools send an explicit strict: false on Responses, Codex and Chat Completions while compatible fixed-field tools stay strict. Anthropic applies strict validation per tool as well; mapping tools keep the ordinary input schema without the strict flag. The fixed execute_code schema stays strict.
