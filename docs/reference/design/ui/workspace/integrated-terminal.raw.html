Integrated terminal and Claude Code launch

The desktop app has real terminals in its center tabs. A Terminal tab opens your login shell (zsh or bash on macOS, PowerShell on Windows) in the current project directory, and a Claude Code tab starts the locally installed claude CLI directly. Each tab is a real PTY in the Electron main process (node-pty) rendered with xterm.js, so colors, full-screen programs, paste, resize and Ctrl+C behave as in any terminal, and the colors follow the App theme. The same terminals are shared with the agent: with the terminal_use tool and your approval it can list the open terminals, read their output and type into the live shell you are looking at, or open a terminal of its own. The Web UI does not expose host command execution.

Why a real PTY

Pipes are not terminals

A child process on plain pipes with TERM=dumb has no terminal device, so interactive programs such as Claude Code lose cursor handling, full-screen redraw, colors and shortcuts.

Terminal semantics belong to a terminal emulator

A <pre> and a single-line <input> cannot interpret ANSI, cursor movement, alternate screens, paste or Ctrl+C; xterm.js does.

One theme contract

Background, foreground, cursor, selection and the ANSI 16-color palette come from the site-wide semantic tokens, so light, warm and custom themes match the rest of the App.

Interaction

Terminal

Opens a login shell in the current project directory. Switching tabs does not terminate the session; closing the Terminal tab terminates the PTY.

Claude Code

A separate entry runs claude directly in the same project directory.

Failure states

When the bridge, the PTY module or the CLI is unavailable, the tab shows an explicit error. Web mode shows no interactive controls. If the project directory does not resolve within a brief wait, the shell starts in the home directory instead of leaving a blank page; once started, a late project response does not restart it.

Theme and ANSI

Theme or Custom CSS changes update only the xterm theme, without restarting the PTY or losing the buffer.

Terminal toolbar

The top shows the preset, process state and actual cwd; the right side has copy, paste, clear, restart and stop. Buttons are compact and borderless; hover and focus follow site-wide tokens.

Keyboard and paste

Cmd/Ctrl+Shift+C copies only when a selection exists; Cmd/Ctrl+Shift+V reads the clipboard and writes to the PTY; ordinary Ctrl+C still sends an interrupt. Cmd+K clears only the current xterm viewport.

Shared with the agent

Every terminal is one native PTY resource in the desktop host, whoever opened it. The agent reaches it through the terminal_use tool: list the terminals, observe one to get a temporary binding and its output, then input, interrupt, resize, release or close, or open a private terminal in a chosen working directory. Each action runs on a single-use ticket issued by the worker (openprogram/host/resources/terminal.py) and redeemed by the desktop host. The tool asks for approval, is unavailable in WeChat and Telegram sessions and in plan mode, and cannot bypass an active task sandbox. Agent input is raw keystrokes, not a command API: "delivered" means only that the input reached the shell, and terminal output is treated as untrusted data. Human typing does not pause the agent, but a changed input revision makes it observe again before it types, and it never retries uncertain input. Releasing the binding leaves the terminal open; closing terminates the shell and is deliberate.

Data flow and trust boundaries

xterm.js ── write / resize ──▶ preload allowlist ──▶ Electron main ──▶ node-pty ──▶ login shell / Claude Code
◀──────── terminal:data / exit ────────◀
terminal_use ──▶ worker ticket ──▶ desktop host (terminal:agent-ticket) ──▶ the same PTY
  • The renderer may select only the shell or claude preset, and cannot submit arbitrary executable/argv.
  • cwd is resolved through realpath and must be a directory; the PTY is bound to the renderer sender and terminal id.
  • Each input is limited to 16 KiB; cols/rows are bounded; replacement processes suppress old-process output.
  • Processes follow tab lifecycles; switching tabs unmounts only the xterm view. Closing the tab, destroying the renderer or explicitly stopping releases the PTY.
  • The PTY runs with the local App user's permissions and provides no remote sandbox.

Scope

The terminal is desktop-only. Remote cloud sessions, a general terminal-session manager, shell-profile editors, persistent command history and a Web host terminal are outside it. Session, file, browser, web, bookmark, history, split, close and drag behavior of other tabs is unaffected by terminal tabs.

Acceptance criteria

  1. A Terminal tab can execute pwd.
  2. The Claude Code entry directly displays the local CLI; input and Ctrl+C reach the process.
  3. When the project list responds normally, cwd is the current main project. If it does not respond, the tab waits only briefly before providing an interactive shell in the home directory, without a blank page.
  4. Pane-width changes synchronize xterm and PTY cols/rows.
  5. The PTY pid stays unchanged across tab switches; closing Claude Code alone does not affect Terminal.
  6. Dark/light, warm and custom theme changes update the terminal and ANSI 16 colors without changing the PTY pid.
  7. Copy, paste, clear, restart and stop work; Ctrl+C keeps interrupt semantics; the toolbar shows running, exited and error.
  8. Focused checks, TypeScript and the Web production build pass.

Shell directory and foreground command lifecycle

The existing desktop PTY resource reports the latest shell directory and foreground command cycle for ordinary macOS zsh and compatible bash 3.2 login shells. These reports are advisory: a command returning zero proves neither external effects nor Agent task success. Background jobs can continue after the foreground cycle finishes. Input delivery still returns phase=delivered or an unconfirmed operation with command_complete=null. Reports never change ownership, leases, approval, input revisions or cancellation.

Metadata and transport

shell_integration?: {
  status: "starting" | "ready" | "unavailable" | "ended",
  mode: "zsh-hooks" | "bash-debug" | null,
  reason: string | null, event_sequence: number,
  cwd: { value: string, event_sequence: number } | null,
  cycle: { id: number, phase: "running" | "finished" | "unknown",
           exit_code: number | null } | null
}

Existing resource reads and events carry this optional field; older hosts may omit it. start_cwd stays immutable and the top-level exit_code belongs to the PTY process. The nested exit_code belongs only to a matched shell cycle. Initial prompts report ready/cwd with cycle=null. Process exit makes an unfinished cycle unknown and ends integration. Last cwd/cycle values remain historical observations, not guarantees about a running child. The Web type accepts metadata without adding a renderer, prompt parser, command API or new store.

Startup and compatibility

zsh retains native -l. Private .zshenv/.zprofile/.zshrc/.zlogin forwarders restore the user's ZDOTDIR value and unset state before sourcing each corresponding user file, capture redirection, and restore the final user directory before appending preexec/precmd hooks. RCS remains authoritative: disabled phases do not re-enable it or install hooks. Existing hook functions remain in place. Readonly callback arrays decline installation. Arbitrary global startup scripts or plugin configurations are not claimed equivalent.

bash retains native -l and receives a one-time PROMPT_COMMAND only if the launch environment did not already define one. The top-level bootstrap captures DEBUG before sourcing. A retained, writable bootstrap installs the minimal DEBUG/prompt pair. Existing custom DEBUG, readonly PROMPT_COMMAND, extdebug, functrace, replaced prompt commands and bash-preexec configurations do not receive integration. Incompatible and unsupported shells remain usable and report unavailable; existing hooks are not overwritten. bash-preexec callback registration remains outside this implementation. Root-parent PID checks prevent nested bootstrap adoption; installed callbacks reject nonroot/subshell reports. No user configuration, shell options or history policy is rewritten.

Protocol and lifetime

Frames use ESC ] 777 ; OpenProgram ; 1 ; nonce ; rootPid ; eventSequence ; kind ; cycleId ; exitStatus ; cwdHex BEL. Kinds are ready, cwd, start and end. Each launch has a random 128-bit nonce; parser checks actual PTY PID, strictly increasing positive safe event sequences, increasing cycle identity and matching completion. UTF-8 absolute cwd is hex encoded using printf/od/tr, limited to16KiB, with no NUL or malformed UTF-8. Frames are limited to36KiB. The incremental parser handles chunk boundaries and releases incomplete candidates after one second. Only valid accepted frames are removed before both live delivery and replay storage; invalid or unrelated output remains unchanged. Output cursors count the same filtered stream.

The shell can read or forge its own nonce, so metadata grants no authority. It contains no command text or environment dump. After three seconds without ready, status becomes unavailable; a later valid first handshake can recover. Missing hooks are not inferred from quiet output; the last report can be stale. Root exit makes a running cycle unknown, never finished.

The existing launch path reads individually packaged scripts through Electron fs and extracts them to a per-launch0700 directory with0600 files, allowing source outside app.asar. Spawn failure or confirmed root exit removes these assets; view reattachment, lease release and hidden panes do not. Old-generation data cannot update replacements. Unsupported preset/platform or asset preparation failure retains the raw terminal. No new settings, terminal engine, CLI or Windows integration is added.

When a later complete private-protocol prefix appears before the current candidate’s BEL, the parser preserves the preceding malformed bytes as ordinary output and reconsiders the later prefix as a new candidate, including across chunk boundaries. The new candidate still requires all existing identity, sequence, cycle and size checks. Invalid preceding output cannot consume a genuine matching completion or prevent later cycles from completing.
