Native page bounds in the built-in browser

The Electron shell DOM toolbar and native WebContentsView must maintain the same page bounds at any shell zoom factor.

Verified gaps

At a shell zoom factor of approximately 1.095 , the renderer sends x=812.63, width=518.64 CSS px, which the main process uses directly as DIP. Correct native bounds should be approximately x=890, width=568. The webpage consequently covers the left chat pane and leaves blank space on the right.

The old occlusion check hides every native Web pane whenever any role=dialog exists in the document. Local working-directory, project and permission menus at the bottom blank the neighboring webpage even when entirely inside the chat pane. Meanwhile, role=menu, role=listbox and several custom fullscreen confirmation overlays are not covered by the same rule.

Multiple split Web panes do not share a global visible flag. Each WebTabPane uses its own body bounds against the same set of current overlays. If a menu covers only the left Web pane, the right pane stays visible. Agent picture-in-picture previews reuse the same registerVisibleWebTabBounds / syncVisible path and publish only the small-window body rectangle, keeping toolbar buttons and the lower-right resize handle outside the native view. Existing MutationObserver, ResizeObserver and scroll/resize listeners republish bounds after overlays close, move or resize. Global flush still batches microtasks within the same tick.

The floating preview always has two layers: a still picture of its page underneath and the live native page on top. The live page shows only while the preview is at rest, fully visible and not occluded; any reason to the contrary is a hold (PipHoldReason in apps/web/components/center-tabs/pip/web-tab-pip-surface.tsx): gesture while it is dragged or resized, clip while the scrolled dock column hides part of it, cover while a menu, dialog or popover overlaps it (the page goes down at once under its last picture), motion while it folds into or unfolds out of the composer's web page chip. The first hold captures a frame and shows it; a capture slower than 150ms (PIP_PICTURE_WAIT_MS) shows the last cached picture meanwhile and replaces it when it arrives. Either way the native bounds go within those 150ms, so nothing that moves next moves under a page that stays put; only when the last hold is released are the final bounds published, and the picture goes once the page has painted there. The page lays out at the preview's virtual viewport (setPipZoom): 1920 wide and as tall as the preview's shape makes it, scaled down to fill the preview edge to edge, so no strip of frame shows beside it whatever the shape. So before it shows for the first time, or at a new size, it is laid out at that size out of sight and waited for until it has painted, plus 250ms (PIP_RELAYOUT_MS) and another paint for pages that lay themselves out from script; it never shows at its standard size or a half-done layout first. Folded into the chip, the page keeps that layout, so it unfolds as it went; a pane that shows the page resets it to the user's zoom. Every picture is cached per tab, so the next unfold starts from it. Closing from the chip or the ✕ folds the frame into the chip over 240ms; showing it again unfolds it over 280ms (apps/web/lib/browser/web-tab/web-tab-pip-motion.ts); with Reduce Motion it appears and goes at once. Background pages are untouched: the native view stays alive the whole time, only its bounds are withheld.

Design

  • The renderer continues sending CSS px measured by getBoundingClientRect() .
  • Only at the renderer IPC boundary does the main process read event.sender.getZoomFactor(), convert CSS px into native DIP, then apply existing integer rounding and nonnegative dimension constraints.
  • sync-visible and the compatibility entry set-bounds use the same conversion. Internal show/hide/transfer paths already using DIP are not scaled again.
  • Shell zoom changes trigger the existing renderer resize listener to remeasure and send current bounds. The main process reads the current zoom factor on every IPC call.
  • Invalid or nonpositive zoom factors are treated as 1 .
  • A DOM overlay occludes the native WebContentsView only when its visible rectangle intersects the current Web body. Working-directory, project and permission menus inside the chat pane must not hide pages in neighboring splits. Dialogs, attachment previews and merge backdrops covering a webpage must still hide the native view; existing bounds observers restore it on close.

Timing while panes move

A native page and the App's DOM reach the display as two separate compositor clients. The renderer measures the page's body while it lays out a frame and sends the bounds in a microtask; the main process moves the view at once, and the browser's frame with the new place reaches the display compositor about a millisecond later. The App's own frame needs the rest of its main frame, a commit and raster first. In a split pane's move both arrive within the same display frame only while the App's frame comes in at the display's deadline: measured on the Dev App at 120 Hz, in good rounds the display draws the moment the App's frame arrives, with no slack, and in a bad round it arrives 0.3 to 0.7 ms after the deadline while the page's frame was on time. Every frame of a move costs about the same, so once one is late the page shows ahead of its frame for the whole move (16 to 18 draws, up to 14 px); one move in twelve to one in four at load 4 to 8, with the same per-frame cost in good and bad blocks.

Nothing in the per-frame reports can fix that: the renderer cannot know its frame will be late, a main process that plays the move from its own schedule is late against a late DOM frame in the same way, and a capture-based presentation signal (beginFrameSubscription) arrives after the draw and would leave the page a frame behind every time. The display compositor does keep surfaces in step when one compositor frame embeds the other, which is how a <webview> guest or an out-of-process iframe is drawn.

Residual: a page ahead of its frame

Because of that, a native page can show away from its frame while a pane moves. Measured on the Dev App, during 24 split-sidebar moves at load 4.6 to 6.2, the page showed away from its frame in 112 of 979 draws, by up to 13 px. The floating preview avoids this for itself. While it is dragged, resized, docked, folded or covered, a hold puts its picture in place of the page (above). A split pane has no such hold, so it keeps the residual.

Considered alternative: pages as guests of the App's frame

An Electron <webview> guest is drawn inside the App's own compositor frame, so it would move, clip and fold with the DOM by construction and take no bounds at all. This was built as an experiment for the floating preview and measured on the Dev App and in Electron 45. In 48 split-panel moves at load 6 to 12, no draw showed the guest away from its frame, and the App's move frames were slightly cheaper (median 3.2 to 3.4 ms against 3.7 to 3.9). The App does not use guests. The reason is how the Agent's input reaches them, measured against a native view of the same page:

  • A guest's frames belong to the App window's frame tree. Chromium delivers typed text and key events sent over CDP to that tree's focused frame. While the App's composer has focus, text the Agent types into a guest lands in the composer, and an Enter could send the user's message.
  • The main process can insert text into a guest's focused element (webContents.insertText) without touching the App's focus. Key events from sendInputEvent reach a guest only after its widget has held focus once. Such key events carry no editing commands, so shortcuts like Command+A do nothing.
  • A click in a guest, whether sent over CDP or with sendInputEvent, moves the App window's keyboard focus into the guest every time. The App can give focus back at once and keep the user's caret and selection, but it does so on its renderer thread. A key the user types before that thread runs goes to the page: with the renderer busy for 150 ms, the keystroke typed right after the Agent's click landed in the page.
  • A native view takes the Agent's clicks, keys and shortcut commands over CDP and never touches the App's focus.

The floating preview is where the Agent's page shows while the user types in the composer. A guest's input routing is therefore as harmful there as it would be in the split panes. Moving a page between a native view and a guest also loads it again, since a document cannot change WebContents. The back/forward history and each entry's scroll position and form values could be carried over (navigationHistory.restore), but script state, open connections, sessionStorage and editors outside form fields could not.

Boundaries and exclusions

Do not forcibly reset user zoom or change split ratios, DOM layout, preload APIs, site zoom, Browser Agent, dependencies or configuration. Electron WebContentsView.setBounds takes DIP while renderer DOM measurements use CSS px. The renderer retains measurement precision; the main process converts units and performs final rounding.

Implementation status

Unit conversion, automated gates and installed-App acceptance are complete.

Pages as guests: the experiment is removed, and no code of it remains. The desktop has no switch, no <webview> wiring and no guest adoption. The preview has no guest surface, and the Agent's browser tool has no relay for guests. The measurements above are kept as the reason guests are not used.
