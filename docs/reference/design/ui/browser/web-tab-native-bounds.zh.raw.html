内置浏览器原生页面边界

Electron shell 的 DOM 工具栏与 native WebContentsView 必须在任意 shell 缩放比例下保持同一页面边界。

已验证缺口

shell 缩放因子约为 1.095 时，renderer 发送 x=812.63, width=518.64 CSS px，主进程直接当作 DIP 使用。正确 native bounds 应约为 x=890, width=568。结果是网页覆盖左侧聊天 pane，并在右侧留下空白。

旧遮挡判断只要文档内存在任意 role=dialog 就隐藏每一个 native Web pane。底部 working directory、project 和 permission 等局部菜单即使完全位于聊天 pane，也会让相邻网页变为空白；同时 role=menu、role=listbox 和若干自定义全屏确认层没有进入同一规则。

浮层与多个 Web pane 的统一规则

浮层类型识别方式native Web 行为
局部 Popover、Dropdown、listbox、tab/split menurole=dialog/menu/listbox逐个 Web body 计算矩形；只隐藏实际相交的 pane。
全屏 modal、确认背景、附件预览data-native-view-occluder=true 或既有 merge backdrop全屏矩形与每个 Web body 相交，因此所有被覆盖 pane 隐藏。
tooltip、toast、drag cue、普通 portaled 内容不进入遮挡 selector不因短暂提示导致网页整体空白。
Desktop main/context/bookmark 原生菜单main process 独立 overlay owner沿用原生菜单生命周期，不由 renderer DOM 重复管理。

多 Web 分屏不共享一个全局 visible flag。每个 WebTabPane 使用自己的 body bounds 与同一组当前浮层分别计算；一个菜单只覆盖左侧 Web 时，右侧 Web 保持可见。Agent 画中画预览复用同一套 registerVisibleWebTabBounds / syncVisible 路径，只发布小窗 body 矩形，工具条按钮和右下角缩放柄留在 native view 之外。浮层关闭、移动或 resize 后由现有 MutationObserver、ResizeObserver 和 scroll/resize listener 重新发布 bounds。全局 flush 仍是同一 tick 内的 microtask 合并。

浮动预览永远有两层：下面是页面的静止画面，上面是活的 native 页面。只有小窗静止、完整可见、没被遮挡时才显示活页面；任何相反的理由都是一次 hold（apps/web/components/center-tabs/pip/web-tab-pip-surface.tsx 的 PipHoldReason）：拖动或调尺寸时是 gesture，侧栏滚动裁掉一部分时是 clip，菜单、对话框或弹出层与它重叠时是 cover（网页立即在上一张截图下面撤下），折叠进或展开出输入框的网页 chip 时是 motion。第一个 hold 截一帧显示出来；截图超过 150ms（PIP_PICTURE_WAIT_MS）还没回来，就先显示上次缓存的画面，回来后再换上。无论哪种情况，native bounds 都在这 150ms 内撤掉，接下来的移动不会发生在一张停在原地的活页面底下；最后一个 hold 解除时才发布最终 bounds，等页面在那里画好再撤掉画面。页面按小窗的虚拟视口排版（setPipZoom）：宽 1920，高度随小窗的比例而定，再缩小到铺满整个小窗，所以不论小窗什么比例，旁边都不会露出一条边框底色。也因此第一次显示或换了尺寸时，先在看不见的地方按新尺寸排好、等它画完，再给靠脚本排版的页面多等 250ms（PIP_RELAYOUT_MS）和一次绘制后才显示，不会先以标准大小或排了一半的样子出现。折叠进 chip 时页面保留这套排版，展开时原样回来；在面板里显示这个页面时再恢复用户缩放。每张画面按标签页缓存，下次展开就从它开始。从 chip 或 ✕ 关闭时小窗在 240ms 内折叠进 chip，再打开时在 280ms 内展开（apps/web/lib/browser/web-tab/web-tab-pip-motion.ts）；开启“减少动态效果”时直接出现和消失。后台页面不受影响：native view 始终存活，只是暂不给它 bounds。

设计

  • renderer 继续发送 getBoundingClientRect() 得到的 CSS px。
  • 主进程只在 renderer IPC 边界读取 event.sender.getZoomFactor()，把 CSS px 转为 native DIP，再执行现有整数化和非负尺寸约束。
  • sync-visible 与兼容入口 set-bounds 使用同一转换；主进程内部已经是 DIP 的 show/hide/transfer 路径不重复缩放。
  • shell 缩放变化会触发现有 renderer resize listener，重新测量并发送当前 bounds；主进程在每次 IPC 上读取当前缩放因子。
  • 无效或非正缩放因子按 1 处理。
  • DOM 浮层只在其可见矩形与当前 Web body 相交时遮挡 native WebContentsView。位于聊天 pane 内的 working directory、project、permission 等菜单不得隐藏相邻分屏中的网页；覆盖网页区域的对话框、附件预览和 merge backdrop 仍需隐藏 native view，关闭后由现有 bounds observer 恢复。

窗格移动时的时序

原生网页和 App 的 DOM 是两个各自独立的合成器客户端，分别送到显示合成器。渲染进程在排一帧时量出网页 body 的位置，在微任务里发出 bounds；主进程立刻移动视图，带着新位置的浏览器帧大约一毫秒后就到显示合成器。App 自己的帧还要先跑完主线程帧、提交和光栅化。分屏窗格移动时，只有 App 的帧赶在显示截止时间之前到达，两者才落在同一显示帧：在开发版 App 上以 120 Hz 实测，正常的轮次里 App 的帧一到显示就立刻绘制，没有余量；出问题的轮次里它比截止时间晚 0.3 到 0.7 ms，而网页的帧准时。一次移动里每帧开销都差不多，所以一旦有一帧迟到，整次移动网页都跑在框前面（16 到 18 次绘制，最多 14 px）；负载 4 到 8 时，十二次移动里有一到三次，好坏两组的每帧开销相同。

逐帧上报的任何改法都解决不了：渲染进程无法预知自己的帧会迟到；主进程按动画自己的时间表摆放视图，面对迟到的 DOM 帧同样会错开一帧；基于截帧的呈现信号（beginFrameSubscription）在绘制之后才到，会让网页每帧都落后一帧。显示合成器只有在一个合成帧嵌入另一个时才会让两者保持同步，<webview> guest 和跨进程 iframe 就是这样绘制的。

残留：网页跑在框前面

因此窗格移动时，原生网页可能显示在偏离它的框的位置。在开发版 App 上，负载 4.6 到 6.2 时做了 24 次分屏侧栏移动，979 次绘制中有 112 次网页偏离它的框，最多 13 px。浮动预览自己避开了这个问题：它被拖动、缩放、停靠、折叠或遮挡时，hold 用它的截图替换网页（见上）。分屏窗格没有这样的 hold，所以残留还在。

考虑过的方案：网页作为 App 帧里的 guest

Electron <webview> guest 画在 App 自己的合成器帧里，因此天然随 DOM 移动、裁剪和折叠，完全不需要 bounds。它曾作为浮动预览的实验实现，并在开发版 App 和 Electron 45 上测量过：负载 6 到 12 时做了 48 次分屏面板移动，没有一次绘制让 guest 偏离它的框，App 的移动帧还略便宜（中位数 3.2 到 3.4 ms，原生为 3.7 到 3.9）。App 不使用 guest，原因在于 Agent 的输入怎样到达它。以下与同一网页的原生视图对照测量：

  • guest 的 frame 属于 App 窗口的 frame 树。经 CDP 发送的文字和按键事件，Chromium 交给这棵树里获得焦点的 frame。App 的输入框有焦点时，Agent 向 guest 输入的文字会落进输入框，一个 Enter 还可能把用户的消息发出去。
  • 主进程可以把文字插入 guest 获得焦点的元素（webContents.insertText），不碰 App 的焦点。sendInputEvent 的按键事件要等 guest 的 widget 持有过一次焦点才能到达。这类按键事件不带编辑命令，所以 Command+A 这类快捷键不起作用。
  • 在 guest 里点击，无论经 CDP 还是 sendInputEvent，每次都会把 App 窗口的键盘焦点移进 guest。App 可以立即还回焦点，并保留用户的光标和选区，但归还要在它的渲染线程上执行。在那个线程执行之前用户敲下的键会进入网页：渲染线程忙 150 ms 时，用户在 Agent 点击之后紧接着敲的键落进了网页。
  • 原生视图经 CDP 接收 Agent 的点击、按键和快捷键命令，从不碰 App 的焦点。

浮动预览正是用户在输入框里打字时显示 Agent 网页的地方，所以 guest 的输入路由在那里和在分屏窗格里一样有害。此外，网页在原生视图和 guest 之间移动时都会重新加载，因为文档不能换到另一个 WebContents。后退/前进历史以及每个条目的滚动位置和表单值可以带过去（navigationHistory.restore），但脚本状态、打开的连接、sessionStorage 和表单字段之外的编辑器带不过去。

边界与排除

不强制重置用户缩放，不修改 split ratio、DOM 布局、preload API、站点缩放、Browser Agent、依赖或配置。Electron 的 WebContentsView.setBounds 接收 DIP，renderer DOM 测量属于 CSS px；renderer 保留测量精度，主进程负责单位转换和最终取整。
